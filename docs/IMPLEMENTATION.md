# Implementation notes

The main process uses a standalone Nest application context. `DesktopModule` provides the CLI runner, queue store and existing operation manager; `WorkspaceController` exposes typed methods through Electron IPC Bridge. Constructor dependencies use explicit `@Inject` tokens so Vite builds do not depend on a decorator-metadata compiler transform. Nest provides dependency injection and lifecycle hooks; no HTTP server is started.

Each IPC method uses `IpcBoundary` to check the sender's window and main frame, validate its payload with the existing Zod schema, and return a sanitized result envelope with a stable error code. Standalone Nest does not automatically apply HTTP guards or pipes. The preload bundles the bridge helper for the sandbox and exposes a readiness promise before the renderer starts. A renderer transport adapter unwraps envelopes into the existing `DesktopApi`, so feature components and demo behavior keep their current contract. Main-to-renderer operation events retain one narrow subscription with an unsubscribe function.

Application shutdown disposes bridge handlers and closes the Nest context. Nest's recovery lifecycle provider stops its polling timer on close. Account checks, preview tokens, operation serialization, stored queue formats and GOG writes remain in the existing services and CLI. Feature-by-feature extraction follows this integration.

Renderer features own their views, data state and pure display models. `features/history/` owns the history view, row model and account-history hook. Clearing history or replacing its API invalidates pending reads. Shared report labels live in `presentation/report-status.ts`, so history does not import the apply-confirmation feature.

`features/library/` owns the game list, achievement list, loading skeleton, search and sorting models, selected-game state, game metadata and achievement cache. Its hook receives a read API, an account guard and a queue-sync callback. Generation checks discard late reads after a new selection, account reset, API replacement or unmount. The workspace still coordinates library-account reconciliation, operation loading and errors, saved queue/history reads and preview invalidation. Queue sync receives a current-selection guard so stale results cannot update another selection. Post-apply refreshes only read achievements for the selected game. Other features will follow this structure in separate PRs.

`features/account/` owns the account menu, auth state, app/CLI versions, startup session check, sign-in/out, ownership checks and account-mismatch recovery. Its hook receives the auth API and one callback that clears account data in the other features. It clears those views before accepting another account. Startup checks share one promise across StrictMode effect replay; fresh session checks bypass that cache. Generation checks ignore superseded auth results and responses after API replacement or unmount. The workspace still serializes actions, observes operation events and coordinates reads after sign-in. Error notices have one shared presentation module.

The workspace follows [A's three-pane layout](design/desktop-workspace.png), with the later UI reviews taking precedence over the original [state concepts](design/WORKFLOW.md). Signed-out users see a blank library and one sign-in action; the queue is hidden. The account menu uses a profile icon and arrow.

The released CLI owns authentication, queue validation and GOG writes. Game and achievement images use trusted GOG image hosts. The CLI currently exposes landscape library thumbnails; portrait metadata lookups would require another request, so artwork remains unchanged under the user's constraint. Demo assets are sample content only, and demo mode never invokes the CLI.

Locked achievements come first, hidden locked achievements next, and unlocked achievements last with newest unlocks first. Descriptions appear below titles. Each eligible row has a direct Add to queue action; hidden details stay concealed until revealed. Game titles use ellipsis and full hover text. Library and achievement reads use local skeletons without a shared loading banner.

The queue groups all saved queues for the signed-in account and remains editable in history. Queued rows show title and description, with calendar and remove controls at the right. Achievement metadata is cached per account and loaded for saved groups without changing the selected game. A compact date dialog supports an explicit date or the current time, preserves seconds, rejects future or invalid times, and requires a chosen offset for repeated local times. The machine zone controls date display and entry; there is no time-zone selector. It refreshes when the window gains focus or becomes visible. Stored timestamps remain UTC instants, so changing the machine zone does not rewrite queue or history dates.

Each group's Apply action runs a dry-run check and opens one final confirmation. The saved snapshot and token bind it to the exact queue, account and game. Confirmed requests are removed under an exclusive queue lock after the immutable report is saved. Failed, unconfirmed and unattempted requests remain. Concurrent edits are preserved, and housekeeping failures retain the confirmed report. Reads can reconcile older confirmed requests only with matching digest-verified snapshots.

Unlock history is a flat list of confirmed achievement unlocks with game names and actual unlock dates. Existing unlocks skipped by an attempt are excluded. Failed or unknown outcomes remain visible under Needs attention. Durable operation records and snapshots stay available for recovery; history does not provide rollback or relocking.

Native controls follow the host OS. Mobile layout supports the local browser demo; installers target desktop. Release builds still require validation on all four native targets, signing and notarization. Local Mac package checks do not prove Windows installation or public signing.
