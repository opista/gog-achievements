# Implementation notes

The main process uses a standalone Nest application context. `DesktopModule` connects the window and app actions to the IPC boundary. In production it imports `WorkspaceModule`, which creates the CLI runner, queue store, process probe and feature services. `WorkspaceController` exposes the module's `WorkspaceApi` through Electron IPC Bridge. Constructor dependencies use explicit `@Inject` tokens so Vite builds do not depend on a decorator-metadata compiler transform. Nest provides dependency injection and lifecycle hooks; no HTTP server is started.

`WorkspaceModule` exports one `WorkspaceService` facade. Every route passes through its recovery gate and the same `OperationCoordinator` before a feature service runs. Internal feature services are not exported for IPC access. Each Nest application context has one operation lock, event stream and preview store; separate contexts do not share them.

| Owner                                 | Responsibility                                                                |
| ------------------------------------- | ----------------------------------------------------------------------------- |
| `WorkspaceService`                    | Stable workspace API, recovery gate and routing through the shared lock       |
| `application/OperationCoordinator`    | Operation serialization and events for every feature                          |
| `features/account/SessionService`     | CLI/platform checks, sign-in/out, account identity and ownership checks       |
| `features/library/LibraryService`     | Validated game and achievement reads                                          |
| `features/queue/QueueService`         | Saved drafts, edits, grouped date saves and reconciliation with saved results |
| `features/apply/ApplyService`         | Preview snapshots, confirmed writes, durable reports and cleanup              |
| `features/history/HistoryService`     | Account-filtered public operation records                                     |
| `features/recovery/RecoveryService`   | Discovery and inspection of surviving writers                                 |
| `features/recovery/RecoveryLifecycle` | Recovery polling and timer cleanup on shutdown                                |

The application layer also owns the shared `PreviewStore` and pure report validation. Session changes, queue edits and current-state checks invalidate the same tokens that apply consumes. Every grouped date-save response must match the account, game and client before the next group is sent. Cleanup rereads surface account or game mismatches; temporary read failures can still return the last valid draft. Reports remain durable before confirmed rows are removed; partial and unknown results never cause an automatic retry. The CLI runner, process probe and versions are injectable without loading Electron, so tests can exercise the production Nest graph with a fake CLI.

Preview ownership includes the snapshot file. Failed, cancelled, replaced and invalidated previews release their files; shutdown releases previews still held by the context. Failed cleanup stays queued for another attempt. Apply takes ownership when it consumes a token and releases the snapshot if validation fails before an operation is saved. Once an operation record exists, its snapshot stays available for history and recovery. Cleanup also preserves snapshots when it cannot determine whether a record was saved. This lifecycle does not prune files left by a process crash; that requires a separate recovery scan.

The process adapter bounds read commands by purpose: help has 10 seconds; doctor, auth status and queue show have 15 seconds; achievements and queue preview have two minutes; games has three minutes. Callers can also cancel these reads with an `AbortSignal`. A deadline or cancellation stops the child, escalates termination after one second if needed, and waits for process closure before releasing the operation lock. It returns a sanitized error and never retries the command. Login, logout, queue edits, CSV export and achievement apply retain their own lifecycle because interruption can leave native windows or changed state. Apply continues to record its process and uncertain results for recovery.

CLI update downloads stream into a private archive owned by the cache. SHA-256 checks and cache manifests read files incrementally; ZIP extraction reads the archive from disk. Metadata and checksum responses retain small byte limits and a 15-second deadline. Archive downloads allow five minutes total and 30 seconds without progress. The cache removes temporary download files before publishing an immutable package. Redirect checks, archive limits, contract probes and verified fallback selection still apply.

Each IPC method uses `IpcBoundary` to check the sender's window and main frame, validate its payload with the existing Zod schema, and return a sanitized result envelope with a stable error code. Standalone Nest does not automatically apply HTTP guards or pipes. The preload bundles the bridge helper for the sandbox and exposes a readiness promise before the renderer starts. A renderer transport adapter unwraps envelopes into the existing `DesktopApi`, so feature components and demo behavior keep their current contract. Main-to-renderer operation events retain one narrow subscription with an unsubscribe function.

Application shutdown disposes bridge handlers and closes the Nest context. Nest's recovery lifecycle provider stops its polling timer on close. Account checks, preview tokens, operation serialization, stored queue formats and GOG writes remain in the existing services and CLI.

Renderer features own their views, data state and pure display models. `features/history/` owns the history view, row model and account-history hook. Clearing history or replacing its API invalidates pending reads. Shared report labels live in `presentation/report-status.ts`, so history does not import the apply-confirmation feature.

`features/library/` owns the game list, achievement list, loading skeleton, search and sorting models, selected-game state, game metadata and achievement cache. Its hook receives a read API, an account guard and a queue-sync callback. Generation checks discard late reads after a new selection, account reset, API replacement or unmount. The workspace still coordinates library-account reconciliation, operation loading and errors, saved queue/history reads and preview invalidation. Queue sync receives a current-selection guard so stale results cannot update another selection. Post-apply refreshes only read achievements for the selected game.

`features/account/` owns the account menu, auth state, app/CLI versions, startup session check, sign-in/out, ownership checks and account-mismatch recovery. Its hook receives the auth API and one callback that clears account data in the other features. It clears those views before accepting another account. Startup checks share one promise across StrictMode effect replay; fresh session checks bypass that cache. Generation checks ignore superseded auth results and responses after API replacement or unmount. The workspace still serializes actions, observes operation events and coordinates reads after sign-in. Error notices have one shared presentation module.

`features/queue/` owns saved queue state, add/remove/date saves, provisional additions, save recovery, queue grouping, the queue pane and its date dialog. The hook receives only queue API methods and an account guard. It checks all owners before publishing a list, preserves other games during single-game edits, and rejects late reads and saves after an account reset, API replacement or unmount. Read revisions prevent older reads from replacing saved or provisional rows. Save recovery surfaces account mismatches before restoring any prior snapshot. The pane receives explicit view data and callbacks, so it can render and be tested without the workspace hook. The workspace retains the shared action lock, errors, preview invalidation, optional library metadata reads and reads after apply.

`features/apply/` owns dry-run preview state, final confirmation, write submission, progress and result views. Its hook receives only preview/apply API methods, an account guard and coordinator callbacks. It consumes each reviewed token before sending the write, rejects duplicate submissions and discards late responses after cancellation, account reset, API replacement or unmount. Account mismatches reach account recovery; other write failures produce an unknown outcome without a retry. A later refresh failure preserves the report. The workspace refreshes durable queues first, then history and the selected game's achievements.

`application/use-operation.ts` owns the shared operation subscription and recovery completion signals. New IPC events take precedence over older startup snapshots. A completed recovery waits for the shared action lock and backend operation to become idle before the workspace checks the session and reads the library. Duplicate idle events do not repeat that check. Leaving recovery returns to browsing even if a follow-up session or library read fails. Subscription cleanup discards events and pending recovery reads from a replaced API or unmounted workspace.

The workspace follows [A's three-pane layout](design/desktop-workspace.png), with the later UI reviews taking precedence over the original [state concepts](design/WORKFLOW.md). Signed-out users see a blank library and one sign-in action; the queue is hidden. The account menu uses a profile icon and arrow.

The released CLI owns authentication, queue validation and GOG writes. Game and achievement images use trusted GOG image hosts. The CLI currently exposes landscape library thumbnails; portrait metadata lookups would require another request, so artwork remains unchanged under the user's constraint. Demo assets are sample content only, and demo mode never invokes the CLI.

Locked achievements come first, hidden locked achievements next, and unlocked achievements last with newest unlocks first. Descriptions appear below titles. Each eligible row has a direct Add to queue action; hidden details stay concealed until revealed. Game titles use ellipsis and full hover text. Library and achievement reads use local skeletons without a shared loading banner.

The queue groups all saved queues for the signed-in account and remains editable in history. Queued rows show title and description, with calendar and remove controls at the right. Achievement metadata is cached per account and loaded for saved groups without changing the selected game. A compact date dialog supports an explicit date or the current time, preserves seconds, rejects future or invalid times, and requires a chosen offset for repeated local times. The machine zone controls date display and entry; there is no time-zone selector. It refreshes when the window gains focus or becomes visible. Stored timestamps remain UTC instants, so changing the machine zone does not rewrite queue or history dates.

Each group's Apply action runs a dry-run check and opens one final confirmation. The saved snapshot and token bind it to the exact queue, account and game. Confirmed requests are removed under an exclusive queue lock after the immutable report is saved. Failed, unconfirmed and unattempted requests remain. Concurrent edits are preserved, and housekeeping failures retain the confirmed report. Reads can reconcile older confirmed requests only with matching digest-verified snapshots.

Achievement history keeps the flat unlock list and adds confirmed locks with their previous unlock dates and local confirmation times. Skipped actions are excluded. Failed or unknown outcomes remain under Needs attention. History does not apply changes; unlocking or locking again requires a fresh queue and confirmation. Durable operation records and snapshots stay available for recovery.

Queue schema 1 accepts legacy unlock rows, explicit `action: "unlock"` rows and `action: "lock"` rows. Lock rows contain `previous_unlocked_at` exactly as observed by the CLI and omit `unlocked_at`. One achievement can have only one queued action. IPC accepts `action` only for addition. Main passes it as a fixed argument to queue create/add and rejects every date save that selects a lock before saving any group. Lock rows have no calendar control. Confirmation states the pending unlock and lock counts.

Report validation matches each action and date to the immutable snapshot. Cleanup removes confirmed locks only for `locked` or `skipped_already_locked`, with a matching action and prior date. A null actual date alone proves nothing. Uncertain, failed and unattempted locks remain queued, including after restart recovery.

Initialization detects `--action` in JSON help for both `queue create` and `queue add`. Older builds keep restoration available while lock controls remain hidden; main also refuses their lock requests. Local development can use the existing CLI directory override. Update the pinned release and checksums only after the new CLI release is published.

Native controls follow the host OS. Mobile layout supports the local browser demo; installers target desktop. Release builds still require validation on all four native targets, signing and notarization. Local Mac package checks do not prove Windows installation or public signing.
